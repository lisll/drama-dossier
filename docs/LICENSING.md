# 卡密授权

剧备使用"卡密激活 + 离线凭证"的授权方式：

- **激活时必须联网**：服务器核销卡密，并把授权和这台电脑绑定。
- **日常使用不联网**：每次都在本机校验服务器的签名。
- **每 24 小时自动联网续期一次**。连续 7 天连不上服务器，软件就会锁定；重新联网后自动恢复，激活页上也可以点「联网重试」。

授权与电脑**固定绑定**，不支持迁移。用户重装系统、或者 Windows 电脑更换主板后，机器码会改变，需要重新兑换一张卡。

> **当前是离线测试版**：不连服务器，只接受一张通用测试卡密。见下文「离线测试版」。正式上线前必须按「删除测试版」整体删除。

| 部分 | 位置 |
|---|---|
| 授权服务器 + 网页管理后台 | [license-server/](../license-server/README.md) |
| 验签、机器码、时钟检查、授权文件校验码、判定（纯逻辑） | `crates/dossier-cardkey` |
| 授权状态机：读写授权文件、锁定规则 | `src-tauri/src/license_state.rs` |
| 桌面端命令、闸门、功能内验权、守护线程、联网 | `src-tauri/src/license.rs` |
| 离线测试版（TEST-MODE） | `src-tauri/src/license_test_mode.rs` |
| 激活页 | `src/license.js`、`src/license.css` |

## 协议

### 卡密

- 由 16 个字符组成，字符集为 `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`，去掉了容易认错的 0、O、1、I。
- 显示格式为 `DDK-XXXX-XXXX-XXXX-XXXX`。
- 用 CSPRNG（密码学安全随机数生成器）生成，约 80 bit 随机量。
- 数据库里只保存 `sha256("drama-dossier/card/v1\n" + 卡密)`，不保存明文。

### 机器码

先把原始标识规范化：去掉花括号和短横线，转成小写，结果必须是 32 位十六进制，并且不能全是 0 或全是 F。

**Windows（v2）**：同时读两样东西。

- 注册表里的 `MachineGuid`（强制使用 64 位视图），这是 Windows 安装时生成的编号；
- 主板固件里的 SMBIOS 系统 UUID，用 `GetSystemFirmwareTable('RSMB')` 读取 Type 1 结构偏移 8 处的 16 个字节（按原始字节转成十六进制）。

`sha256("drama-dossier/machine/v2\nwindows\n" + 规范化的 MachineGuid + "\n" + 主板 UUID)`

只用 MachineGuid 时，改一下注册表或者克隆系统盘，就能让两台电脑的机器码相同；加上主板 UUID 后，这两种做法都失效。代价是换主板后需要重新激活。

主板 UUID 读不到，或者是占位值时，退回 v1 公式，只用 MachineGuid，不会锁定。占位值包括全 0、全 F、只有一两种字符，以及不少杂牌主板出厂时写死的 `03000200-0400-0500-0006-000700080009`。

**macOS、Linux（v1）**：

`sha256("drama-dossier/machine/v1\n" + 平台 + "\n" + 规范化后的原始标识)`

- macOS：读 `IOPlatformUUID`，它本身就是硬件编号。
- Linux：读 `/etc/machine-id`，读不到时回退 `/var/lib/dbus/machine-id`。

读不到 MachineGuid、IOPlatformUUID 或 machine-id 时直接锁定，不会退回到主机名这类容易变化或伪造的弱指纹。

### 授权凭证

格式为 `base64url(payload) "." base64url(Ed25519 签名)`，两段都不带填充，并且必须是唯一的规范编码。签名覆盖的内容是：

`"drama-dossier/license/v1\n" + payload 原始字节`

payload 是 JSON 对象，序列化时按键名排序、使用紧凑分隔符、只包含 ASCII 字符：

| 字段 | 含义 |
|---|---|
| `v` | 版本号，固定为整数 1 |
| `kid` | 签名公钥 `sha256` 的前 16 位十六进制 |
| `lid` | 服务器上的电脑记录编号 |
| `mid` | 机器码 |
| `plan` | 卡种：`trial` / `month` / `quarter` / `year` / `lifetime` |
| `until` | 使用权到期时间（Unix 秒）；永久卡为 `null` |
| `iat` | 签发时间 |
| `exp` | 凭证到期时间：`min(iat + 7 天, until)`。永久卡也会到期，需要定期续签 |

客户端按以下顺序判定，任何一步失败都会锁定：

1. 格式
2. 签名（逐一尝试内置公钥，`kid` 必须与签名公钥一致）
3. 严格解析载荷（字段必须一个不多、一个不少，不能有重复键，整数必须小于 2^53，不接受布尔值、浮点数或负数）
4. 机器码
5. 时钟回拨（`now + 600 < max(last_seen, iat)` 视为回拨）
6. 有效期（`now >= exp` 或 `now >= until` 都算过期）

两端的实现由 `crates/dossier-cardkey/tests/vectors_v1.json` 中的 48 条测试向量逐条对照。这些向量由 `license-server/tests/vectors.py` 生成，修改协议后必须重新生成，同步修改 `tests/vectors.rs` 里的 `EXPECTED_CASES`，并且一起提交。

### 授权文件

凭证保存在应用配置目录下的 `license.json`，除凭证外还有三项：

| 字段 | 含义 |
|---|---|
| `last_seen` | 见过的最晚时间，用来发现系统时间被往回调 |
| `revoked` | 服务器已明确停用这台电脑 |
| `mac` | 校验码：`HMAC-SHA256(程序内置密钥, 机器码 + 凭证 + last_seen + revoked)` |

`last_seen` 和 `revoked` 没有服务器签名，所以用校验码绑在一起。手改任何一个数字，校验码就对不上，判为"授权信息无效"，需要重新激活。缺少任何字段的老格式文件同样判为无效。

### 卡种规则

| 卡种 | 时长 | 规则 |
|---|---|---|
| 试用卡 | 3 天 | 只能在从未激活过的电脑上使用 |
| 月卡 / 季卡 / 年卡 | 30 / 90 / 365 天 | 在已有到期时间的基础上叠加；已过期则从兑换当天开始算 |
| 永久卡 | 不限 | 兑换后，这台电脑不能再兑换其他卡 |

时长统一在 `license-server/src/dd_license/plans.py` 里配置。生成卡密时会把当时的天数复制进卡密记录，之后修改配置，不影响已经卖出去的卡。

## 客户端多层验权

| 层 | 做什么 |
|---|---|
| ① 激活页 | 未授权时全屏遮挡界面。这一层只影响体验，删掉它也绕不过后面几层 |
| ② 总闸门 `license::gate` | 包裹 `invoke_handler`。未授权时，白名单之外的**所有**命令都会被拒绝，以后新增的命令也默认被锁 |
| ③ 功能内验权 `license::guard()` | 每个主要功能入口的第一行都调用它。每次从磁盘重新读取凭证并完整验签，不依赖缓存；函数标记为 `#[inline(always)]`，会被展开到各个调用处 |
| ④ 守护线程 | 每隔 3–9 分钟（随机间隔）重新验签一次，每 24 小时联网续签一次（失败后 1 小时重试）。启动时如果凭证已过期，立即续签 |
| ⑤ 金丝雀自检 | 每次验权时，用内置的"已知坏签名"和"已知好签名"各验一次。如果验签逻辑被改成永远返回通过，坏签名也会通过，自检随即失败 |

调用 `guard()` 的位置：
- `generate_package`
- `plan_erase` 和 `run_erase`
- `apply_rename`、`fix_bitrate`、`transcode_execute`、`dedup_demo_execute`
- `export_draft` 和 `generate_mount_copy_csv`
- 所有 AI 调用的统一入口 `ai::http_client`

未授权时也放行的命令：授权自身的四个命令、看日志（`open_log_dir`、`read_recent_logs`），以及停止转码、查询擦除状态（`transcode_stop`、`erase_status`）。授权在长任务中途失效时，用户必须还能把任务停下来。

### 锁定规则

- **每次都重新判断**。偶发的读取失败（比如杀毒软件短暂占用授权文件）、时钟被调回去又调回来，下一次检查就会自动恢复，不会把整次运行锁死。
- **只有自检失败会在整次运行内保持锁定**：说明程序被改过，重启前不再放行。
- **服务器停用会写进授权文件**：刷新页面、重启软件都无效，只有激活或续签成功、拿到新凭证才会解除。
- **只有服务器明确拒绝才算停用**：续签时，只有收到 `token_invalid`、`machine_revoked`、`license_expired`、`not_activated` 这四个错误码才会锁定。其他错误一律当作"暂时连不上"，凭证还在有效期内就照常使用。这些错误包括 404、422、413、429、5xx，以及代理或防火墙返回的网页。
- **运行期间在内存里也记一份最晚时间**：运行中删掉或替换授权文件，绕不过时钟回拨检查。
- **连续 1 小时写不进授权文件就锁定**（比如文件被设成只读）。写入失败会记录日志，恢复可写后自动放行。
- 状态在"有效"和"锁定"之间变化时（包括后台续签成功），会通知前端；前端收到"恢复有效"后自动进入主界面。

正式版（release）构建中，一次完整验权平均约 0.3 毫秒，见 `license::tests::full_check_path_is_fast`，2026-10-27 在开发服务器上实测。正常使用时不会联网，也不会弹窗。

### 能防住与防不住

**能防住**：
- 把授权文件拷到另一台电脑：凭证和校验码都绑定机器码。
- 用记事本修改授权文件。
- 运行期间把系统时间往回调。
- 自建假的授权服务器：签名验不过。
- 改 Windows 注册表或者克隆系统盘来共用授权。
- 用开发者工具修改界面。正式版不带开发者工具。

**防不住**：
- 熟悉逆向工程的人直接修改二进制文件，或者从程序里找出校验码的密钥自己重算。多层验权的作用，是把破解从"改一处"变成"找到并改掉十几处分散的检查，同时还要绕开自检和守护线程"，而且每发一个新版本都得重新来一遍。要进一步提高门槛，只能靠商业加壳，或者把核心功能放到服务端去执行。
- 长期把系统时间设在过去，并且每次启动前都还原一份旧的授权文件；或者用虚拟机快照反复回到同一个时间点。这是所有离线验证共同的限制。
- 拿到源码后自己编译一个去掉检查的版本。仓库公开时这一条无法防住，见「上线检查清单」。

## 离线测试版（TEST-MODE）

当前代码默认就是测试版：`src-tauri/Cargo.toml` 的 `license-test-mode` 开关默认打开。

- 激活页显示「测试版授权」标识，只接受通用测试卡密 **`DDK-TEST-CARD-2345-6789`**（不区分大小写，可以带空格或短横线），输入其他卡密会提示"测试版只接受测试卡密"。
- 激活时不联网：程序用内置的测试私钥，为本机机器码签发一份 30 天的试用凭证。之后的验签、机器绑定、写入授权文件、到期判断、防改校验，走的都是正式版代码。
- 30 天到期后，再输入一次测试卡密即可续用。测试版不会联网续签。
- 测试私钥就写在 `license_test_mode.rs` 里，拿到源码的人都能签发测试凭证，所以**测试版只能发给内部测试人员**。
- 测不到的部分：联网续签、服务器停用、错误码分类。这些靠单元测试，以及对着本机 `license-server` 跑的端到端测试来验证（见下文「本地开发」）。

### 删除测试版

测试通过后执行。所有接入点都标了 `TEST-MODE`，用 `git grep -n "TEST-MODE\|license-test-mode\|license_test_mode"` 就能找全：

1. 删除 `src-tauri/src/license_test_mode.rs`，以及 `src-tauri/src/lib.rs` 里对应的 `mod` 声明。
2. 删除 `src-tauri/Cargo.toml` 中的 `[features]` 段（`default` 和 `license-test-mode`）。
3. 删除 `src-tauri/src/license.rs` 中所有标了 `TEST-MODE` 的代码块，包括编译期检查、`trusted_keys` 里的测试公钥分支、`license_activate` 里的测试卡密分支，以及 `test_mode()` 和 `LicenseStatus` 里的 `test_mode` 字段。
4. 删除 `src/license.js`、`src/license.css` 中标了 `TEST-MODE` 的部分。
5. 运行 `scripts/check.sh` 并全部通过。

`dossier-cardkey` 的 `test-issuer` 开关保留，单元测试要用它签发凭证；正式版的依赖里不会开启它。

忘了删就填入正式公钥的话，编译会直接失败，并提示先删除测试版，所以测试版不会混进正式版。

## 本地开发

- **调试构建默认跳过授权检查**：用 `cargo tauri dev` 本地运行时不需要激活，日志里会记一条警告。想在调试构建里测授权，设置 `DD_LICENSE_DEV_BYPASS=0`。
- 正式版（release）构建里没有这个开关；自动测试（`cargo test`）也不会跳过，测试照样走真实检查。
- 调试构建还可以用 `DD_LICENSE_SERVER=http://127.0.0.1:8200` 和 `DD_LICENSE_DEV_PUBKEYS=<公钥>` 连接本地授权服务器，端到端测试 `license::tests::e2e_against_local_server` 的用法见它的文档注释。

## 密钥轮换应急

私钥泄露时，攻击者可以伪造任意授权。按以下步骤处理：

1. 在服务器上执行 `license-admin keygen --out 新路径`，然后把 `DD_LICENSE_KEY_FILE` 指向新私钥，重启服务。从这一刻起，新签发的凭证都使用新私钥。
2. 把客户端的 `PRODUCTION_KEYS` 改成**只包含新公钥**，然后发布新版本。旧版本客户端仍然信任旧公钥，攻击者伪造的凭证在旧版本上依然有效。因此只能通过强制升级止损。
3. 老用户升级到新版本后，本地凭证是旧私钥签发的，新版本验不过，会显示"授权信息无效"，用户需要重新激活。服务器认得这台电脑，用户输入原来那张卡密时，服务器按"本机重复兑换"处理，不会消耗新卡，会直接签发新凭证。

正常的计划内轮换（私钥没有泄露）步骤如下：
1. 先发布一个客户端版本，`PRODUCTION_KEYS` 里同时包含新旧两把公钥。
2. 等大多数用户升级完成后，服务器切换到新私钥，同时把旧公钥填进 `DD_LICENSE_EXTRA_PUBKEYS`。这样老用户手里旧私钥签发的凭证仍可用来续签，续签拿到的新凭证则由新私钥签发。
3. 再发布一个只保留新公钥的版本。7 天以后，清空 `DD_LICENSE_EXTRA_PUBKEYS`。

私钥泄露时**不要**填 `DD_LICENSE_EXTRA_PUBKEYS`，否则攻击者伪造的凭证也能拿来续签。
