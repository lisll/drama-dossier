## 2. 授权与发布（A）

### A1 发行包默认是离线测试版授权【高】

**现状与证据**
- [src-tauri/Cargo.toml](../src-tauri/Cargo.toml#L13) `default = ["license-test-mode"]`：不加任何参数构建就是测试版。
- [.github/workflows/build-windows.yml](../.github/workflows/build-windows.yml#L63) 直接 `cargo tauri build`；[.github/workflows/desktop.yml](../.github/workflows/desktop.yml#L228-L233) 的 tauri-action 也没有关闭默认 feature。
- desktop.yml 的 `release` 任务在推 `app-v*` 标签时把安装包传到 **GitHub Release**（[L258-L289](../.github/workflows/desktop.yml#L258-L289)，`prerelease: true`）。远端是 `github.com/lisll/drama-dossier`，若仓库公开，任何人都能下载这个测试版。
- 激活失败的提示直接回显测试卡密：[src-tauri/src/license.rs](../src-tauri/src/license.rs#L645-L648)。卡密也写在 [docs/LICENSING.md](LICENSING.md#L157)。
- 防误发断言 [license.rs](../src-tauri/src/license.rs#L117-L122) 只在「已填正式公钥」时才触发；现在正式公钥为空，所以不拦。

**判断**：测试版本身是有意设计（LICENSING.md 写明「只能发给内部测试人员」），问题在于**没有任何机制阻止它进入公开发布渠道**。

**影响**：拿到安装包的人用测试卡密可无限续 30 天；测试私钥写在源码里（[license_test_mode.rs](../src-tauri/src/license_test_mode.rs#L21-L24)），拿到源码的人还能自签凭证。

**方案（推荐）**：把「测试版 / 正式版」变成显式选择，并让正式发布在编译期把关。
1. `default = []`。测试版改为显式 `--features license-test-mode` 构建。
2. 新增 feature `official-release`，在 `license.rs` 加两条编译期断言：
   - 开了 `official-release` 时 `PRODUCTION_KEYS` 不得为空；
   - `official-release` 与 `license-test-mode` 不得同时开启。
3. CI 拆成两条路：
   - **内测包**：`workflow_dispatch` 手动触发，带 `license-test-mode`，只上传到 Actions Artifacts，**不进 Release**；
   - **正式包**：`app-v*` 标签触发，带 `official-release`，进 Release。正式公钥没填时这条路会编译失败——这正是想要的效果。
4. 测试版的拒绝文案改成「测试版只接受内部测试卡密，请联系发放人」，不再回显卡密原文。

**不选的替代方案**：只在 CI 里加 `--no-default-features`。缺点是本地 `cargo tauri build` 仍然默认出测试版，防线只在 CI 一处，容易被手工打包绕过。

**改动范围**：`src-tauri/Cargo.toml`、`src-tauri/src/license.rs`（断言 + 文案）、两份 workflow、`docs/LICENSING.md`。

**验证**：四种 feature 组合各编一次（无 / 仅测试 / 仅正式 / 两者都开），确认「仅正式且无公钥」与「两者都开」编译失败、其余成功；默认构建的界面不出现「测试版授权」徽标。

**已确认**（§9 Q1）：正式服务器上线前不发 Release，内测包只走 Actions Artifacts。

### A2 回滚授权文件 + 拨回时钟可离线续用【中】

**现状与证据**
- 授权文件里「见过的最晚时间」和「已停用」两项靠 HMAC 防改，密钥是程序常量：[crates/dossier-cardkey/src/seal.rs](../crates/dossier-cardkey/src/seal.rs#L15)。
- 时钟下限取 `max(文件里的 last_seen, 内存里的 last_seen)`：[src-tauri/src/license_state.rs](../src-tauri/src/license_state.rs#L198-L201)；进程重启后内存值归零。

**影响**【推断】：备份一份「停用前」的授权文件 → 被停用后恢复备份 → 断网 + 把系统时间拨回凭证有效期内，即可继续使用，直到凭证本身过期（默认签发后 7 天）。需要同时满足「离线」和「改系统时间」，所以定为中。

**方案（推荐）**：增加一个**独立于授权文件**的时间锚点。
- 把 `last_seen` 再写一份到系统凭据库（Windows 凭据管理器 / macOS 钥匙串；项目已有 `SecretStore` 接口，见 PROJECT_REVIEW §8.6）。
- 校验时取「文件、凭据库、内存」三者最大值作为下限。恢复旧文件只能回滚其中一处。
- 「已停用」标记同样双写；任一处为已停用即视为停用。

**边界说明**：这只提高门槛，挡不住会逆向的人（对照文档 §2.7 的 Grove Max 也是同一级别的本地校验）。真正的上限由「凭证有效期」决定，可考虑把默认离线有效期从 7 天缩短，见 §9 Q2。

**改动范围**：`license_state.rs`、`dossier-runtime` 的 `SecretStore` 实现（当前是「权限收紧的文件」，不是 OS 钥匙串，需要先补真实实现）。

**验证**：单测——恢复旧授权文件后，凭据库里更晚的锚点仍然生效；凭据库不可用时退回现有逻辑，不锁死用户。

### A3 没有最低版本强制升级【中】

**现状**：服务端只记录 `last_app_version`，全仓库没有最低版本判断（grep 无结果）。对照文档 §2.9 / §11 #6 的 `client_too_old` 是成熟做法。

**影响**：发现有漏洞的旧版本后，无法让它停止工作。

**方案**：
- 服务端配置 `min_app_version`；激活与续签接口在版本过低时返回 `client_too_old`，附下载地址。
- 客户端收到后进入「需要更新」状态：保留已生成的文件，不再允许发起新任务。
- 离线状态下不触发（只能在下次联网续签时生效），这是可接受的。

**改动范围**：`license-server/src/dd_license/{config,service,api}.py`、`src-tauri/src/license.rs`、`src/license.js`。

**已确认**（§9 Q3）：正式上线前做，本轮不做。

## 3. 任务控制（B）

### B1 停止开关全局共用、停止后不复位【高】

**现状与证据**
- 只有一个全局开关 `TRANSCODE_CANCEL`：[src-tauri/src/toolbox.rs](../src-tauri/src/toolbox.rs#L42)；只在转码开始时复位（[L1806](../src-tauri/src/toolbox.rs#L1806)）。
- 所有 ffmpeg 调用都看它（[run_ffmpeg L443](../src-tauri/src/toolbox.rs#L443)），包括码率修复与材料线程（`content.rs` 共 8 处检查）。
- 前端只有转码页有停止按钮（[src/main.js](../src/main.js#L3254)），调用 `transcode_stop` 时不带任务标识。

**影响**
1. 点过一次「停止转码」后，码率修复每一集都立刻报「ffmpeg 已被停止」，直到下一次转码复位为止。
2. 两部剧同时转码时，停一个等于停两个（输出目录互斥只防同一目录，不防不同剧并发）。
3. 新任务启动时的复位，可能让正在收尾的旧任务「忘了自己被停过」，跳过清理（[L2020](../src-tauri/src/toolbox.rs#L2020)）。

**方案（推荐）：每个任务一个取消令牌**
- 新增 `CancelToken`（内部是 `Arc<AtomicBool>`）和一张「活动任务表」（`Mutex<HashMap<任务ID, CancelToken>>`）。
- 任务开始时登记，结束时由一个守卫对象（RAII，作用域结束自动执行）注销，保证任何返回路径都不留残余。
- `run_ffmpeg` 增加令牌参数，不再读全局变量；材料线程拿同一个任务的子令牌（见 B2）。
- `transcode_stop` 保持无参数，语义改为「停止所有转码类任务」，前端不必改；码率修复另外登记成 `bitrate` 类任务，配一个自己的停止入口（见 E2）。

**不选的替代方案**：保留全局变量，只在任务结束和码率修复开始时多复位一次。改动小，但影响 2、3 依然存在。

**改动范围**：`toolbox.rs`（`run_ffmpeg` 及其 7 处调用、`transcode_blocking`、`fix_bitrate_blocking`）、`content.rs`（8 处检查与 2 处 `run_cancellable`）。

**验证**：单测——停止任务甲不影响任务乙；任务结束后表中无残留；停止转码后立刻跑码率修复能正常完成。

### B2 编码失败后材料线程照跑【中】

**现状与证据**：编码返回后才汇合材料线程（[toolbox.rs L1998-L2006](../src-tauri/src/toolbox.rs#L1998-L2006)）；材料线程只在「被停止」时提前退出，所以编码失败时它会继续调 LLM 和生图接口。

**影响**：编码已失败，成片不可用，但用户仍然为剧名、简介、海报付了 API 费用。

**方案**：在 B1 的令牌上分两级——任务令牌、材料子令牌。编码返回 `Err` 时先取消材料子令牌，再汇合。材料线程在**每次计费调用之前**检查令牌（已经发出的 HTTP 请求不中途打断，避免付了钱却丢结果）。

**已确认**（§9 Q4）：已生成的材料保留在输出目录，报告里标明「成片未完成」。

### B3 去重验证不能停止，超时只杀 Python【中】

**现状与证据**：`dedup_demo_execute` 用不可取消的 `.run()`、超时 1800 秒（[toolbox.rs L2514-L2519](../src-tauri/src/toolbox.rs#L2514-L2519)）；超时处理只 `child.kill()` 直接子进程（[crates/dossier-runtime/src/command.rs](../crates/dossier-runtime/src/command.rs#L265-L285)），Python 拉起的 ffmpeg 不在其中。

**影响**【推断】：用户无法中止；超时后 ffmpeg 变成孤儿进程继续占 CPU 并写文件。

**方案**
- 改用 `run_cancellable` + B1 的令牌，登记为可停止任务。
- `dossier-runtime` 增加「杀整个进程树」：Unix 启动时 `setpgid` 新建进程组，停止时向整组发信号；Windows 用 Job Object（关闭句柄时连带结束所有子进程）。所有长任务（ffmpeg、Python、whisper）都受益。

**改动范围**：`crates/dossier-runtime/src/command.rs`（新增能力 + 单测）、`toolbox.rs`。

### B4 单条 ffmpeg 固定 600 秒超时【中】

**现状与证据**：`FFMPEG_TIMEOUT_SECS = 600`（[toolbox.rs L37](../src-tauri/src/toolbox.rs#L37)），注释写「短剧分集都在几分钟量级」；但设置允许单集最长 3600 秒（[crates/dossier-core/src/settings.rs](../crates/dossier-core/src/settings.rs#L116)）。

**影响**【推断】：深度处理的滤镜链用 CPU 编码长集时会超过 10 分钟，被杀后整轮失败。

**方案（推荐）**：超时按本条命令的输入时长计算：`max(600, 时长秒 × 系数)`，系数先取深度处理 8、其他 4，上限 4 小时。系数需在低配机器上实测后再定。

**后续可选**：改用「无进度超时」（ffmpeg 输出 `-progress` 后 N 分钟没有新进度才判定卡死），最准确，但改动较大，本轮不做。

## 4. 产物完整性（C）

### C1 成片直接写最终名、失败不清理、旧集残留【高】

**现状与证据**
- 三种模式都直接写最终文件名并带 `-y`：微调写同名文件（[toolbox.rs L1079](../src-tauri/src/toolbox.rs#L1079)），重组写 `第NN集.mp4`（[L1320](../src-tauri/src/toolbox.rs#L1320)），深度处理写进 `视频成片/`（[L1648](../src-tauri/src/toolbox.rs#L1648)）。
- 只有「用户主动停止」才清理本次产物（[L2019-L2032](../src-tauri/src/toolbox.rs#L2019-L2032)）；其他失败直接 `Err(error)` 返回，已完成的集留在目录里。
- 没有任何逻辑删除上一轮多出来的集。

**影响**
1. 进程崩溃或被杀会留下截断的 mp4，文件名和正常成片一样，肉眼分不出来。
2. 第 5 集失败时，第 1–4 集是新的、第 6 集以后是上一轮的，目录里新旧混杂。
3. 重新分集时集数变少（12→10），旧的第 11、12 集残留，后续生成报审包或挂载时会被当成正式成片。

对照文档 §4.5：成熟做法是「publish 原子写入，失败不留半个包」。

**方案（推荐）**
1. **单集先写临时名**：编到同目录的 `.第NN集.part.mp4`（点开头，扫描器会跳过；保留 `.mp4` 后缀让 ffmpeg 正确识别格式）。成功后 `rename` 成最终名。同目录 rename 是原子的，不会出现半截文件。
2. **任何失败都清理**：把现有「停止才清理」改成「失败即清理本次产物」，停止只是失败的一种。清理范围沿用现有的 `produced` 列表与「目录是否本次新建」规则，不碰用户自己的文件。
3. **成功后清理多余旧集**：只针对重组与深度处理（微调输出与源文件同名，没有「多余集」）。删除条件三项同时满足才删：
   - 在本工具的输出目录里（已有归属标记 `.dossier-owner.json` 校验）；
   - 文件名精确匹配 `第\d{2,}集.mp4`；
   - 不在本次产物列表中。

**已确认**（§9 Q5）：满足三个条件的多余旧集直接删除。

**改动范围**：`toolbox.rs` 三种模式的输出路径、`transcode_blocking` 的错误分支、新增「清理多余集」函数。

**验证**：单测覆盖「第 3 集失败 → 目录里没有本次任何成片」「12 集重跑成 10 集 → 第 11、12 集被清理」「目录里用户自己的 `花絮.mp4` 不受影响」。

### C2 深度处理输出目录没被扫描器排除【中】

**现状与证据**
- 扫描器会进入剧目录下一层子目录找素材，只排除 `报审包 / 微调输出 / 重组输出` 三个名字（[crates/dossier-core/src/scanner.rs](../crates/dossier-core/src/scanner.rs#L15)）。
- 深度处理没设输出根目录时，落点是 `<剧目录>/深度处理`（[settings.rs L402](../crates/dossier-core/src/settings.rs#L402)），并在其中写 `简介.txt`（[src-tauri/src/content.rs](../src-tauri/src/content.rs#L1632)）。
- 扫描器取简介的规则是「文件名含"简介"、先遇到的那个」（[scanner.rs L76-L82](../crates/dossier-core/src/scanner.rs#L76-L82)）。

**影响**【推断，需实测】：下一次扫描时，AI 生成的简介可能被当成「素材自带的简介」。
- 剧目录本来没有简介时，一定会被误读。
- 剧目录有简介时，取决于目录遍历顺序；Windows NTFS 按名称排序，「深」排在「简」前面，生成的那份可能先被读到。

**方案**：把 `深度处理` 加入排除列表；顺手把这个列表改成从各模式的输出目录名常量汇总生成，避免以后新增模式时再漏掉。

**验证**：扩展现有单测 `scan_skips_product_subdirs`（[scanner.rs L274](../crates/dossier-core/src/scanner.rs#L274)），加入 `深度处理/简介.txt` 场景。

### D1 CUDA 版 whisper：下错包、zip 当 exe、没有自检【高】

**现状与证据**
- 下载地址是 `.../b5454/whisper-bin-x64.zip`（[src-tauri/src/downloads.rs](../src-tauri/src/downloads.rs#L346)）。经 GitHub API 核实，这个文件 **8.9 MB，是 CPU 版**；CUDA 版是同一发布下的 `whisper-bin-win-cuda-11.8.0-x64.zip`（285 MB，与代码注释里的「约 285 MB」一致）。
- 下载后直接把 zip 改名成 `whisper-cli.exe`，中间没有解压（[src-tauri/src/models_install.rs](../src-tauri/src/models_install.rs#L238-L242)）。
- 改名成功就写 `cuda.ready` 标记并删除 CPU 版备份；代码注释说「靠装完能跑起来的自检把关」，但实际没有自检。
- 完整性是 `Integrity::None`，注释说「上游不发布哈希」。实际上 GitHub API 已为该发布的每个文件提供 sha256 摘要（例如 CUDA 11.8 包为 `e81c86c5…d027`），而且 `b5454` 是固定标签，可以钉住。

**影响**：Windows + N 卡用户，第一次启动后 ASR 永久损坏——`whisper-cli.exe` 实际是一个 zip，CPU 版已被删，`cuda.ready` 标记阻止重试。界面上表现为语音转写失败，用户无法自行恢复。

**方案（推荐）**
1. 地址改为 `whisper-bin-win-cuda-11.8.0-x64.zip`，完整性改为 `Integrity::Sha256(...)`。
2. 下载到临时目录 → 解压到 `whisper.cuda-staging/` → 在 staging 里实跑一次 `whisper-cli.exe --help`（或转写一段 1 秒静音），**自检通过**才整目录替换。
3. 替换是「目录级」的：旧目录先改名为备份，新目录改名就位，成功后删备份；失败则还原。CUDA 包附带 cublas 等 DLL，只换一个 exe 不够。
4. 自检失败时保留 CPU 版，写 `cuda.failed` 标记，避免每次启动都重下 285 MB；设置页提供「重试 GPU 加速」按钮清除标记。
5. **自愈已损坏的用户**：启动时检查 `whisper-cli.exe` 前两个字节；如果是 `PK`（zip 文件头）而不是 `MZ`（exe 文件头），删除它和 `cuda.ready`，重新从安装包复制 CPU 版。

**已确认**（§9 Q6）：CUDA 11.8。

**改动范围**：`downloads.rs`、`models_install.rs`；复用现有 `extract_zip`（[toolbox.rs L2773-L2795](../src-tauri/src/toolbox.rs#L2773-L2795)）。

**验证**：Windows CI runner（无 GPU）上验证「下载 + 解压 + 结构检查」与「检测到 PK 头 → 自愈」；真实 GPU 推理只能在用户机器或带 N 卡的测试机上确认。

### D2 安装器下载后不校验就执行【高】

**现状与证据**
- Python 安装器：`download_file` 不做任何校验（[toolbox.rs L3004](../src-tauri/src/toolbox.rs#L3004)），下完直接静默运行（[L3013-L3018](../src-tauri/src/toolbox.rs#L3013-L3018)）。
- tesseract 安装器：首选源是第三方代理 `ghfast.top`（[models_install.rs L59](../src-tauri/src/models_install.rs#L59)），下完同样直接运行（[L669-L687](../src-tauri/src/models_install.rs#L669-L687)）。
- curl 参数 `-fL` 会跟随任意重定向，没有限制只走 HTTPS（[toolbox.rs L2672-L2685](../src-tauri/src/toolbox.rs#L2672-L2685)）。

**影响**：代理被篡改、DNS 被劫持或重定向被降级到 HTTP 时，用户电脑会以当前用户权限执行攻击者的程序。走第三方代理是常态而不是例外，所以定为高。

**方案**
1. 两个安装器都改走 `fetch_with_fallback` + `Integrity::Sha256`。哈希来源：
   - Python 3.11.9：从 python.org 官方文件计算后写入代码（官方页面另有 Sigstore 签名可交叉核对）；
   - tesseract 5.4.0.20240606：GitHub 发布未提供摘要，从官方源下载后计算写入。代理源与官方源用**同一个哈希**，代理即使被篡改也过不了校验。
2. `download_file` 的 curl 参数加 `--proto =https --proto-redir =https`，所有下载都只走 HTTPS。
3. 规定所有「下载后会被执行」的文件必须是 `Integrity::Sha256`；`Integrity::None` 只允许用于数据文件，并在代码注释里写明原因。

**改动范围**：`toolbox.rs`（Python 安装、`download_file`）、`models_install.rs`（tesseract）。

**验证**：单测——哈希不符时安装器不会被执行，临时文件被删除；`downloads-tests` 中补「代理源与官方源共用哈希」的用例。

## 6. 工具箱（E）

### E1 批量改名：单阶段执行，会覆盖丢文件【高】

**现状与证据**（[src-tauri/src/toolbox.rs](../src-tauri/src/toolbox.rs#L340-L377)）
- 预检做了三件事：源文件存在、`target.exists()`、目标名去重；去重用的 `HashSet` 区分大小写。
- 执行时逐个 `rename(...)?`，中途失败直接返回，不回滚。

**影响**（Windows 与 macOS 的默认文件系统都**不区分大小写**）
1. **丢文件**：两个目标名只差大小写（如 `EP01.mp4` 与 `ep01.mp4`）能通过预检；第二次 rename 会把第一次的结果覆盖掉，那个文件就没了。
2. 只改大小写（`Ep01.mp4 → ep01.mp4`）会被误报「目标名已存在」，因为系统认为它就是自己。
3. 互换或链式改名（A→B、B→A；1→2、2→3）一律被拒绝，而这恰好是「重新编号」最常见的场景。
4. 第 30 个文件改名失败时，前 29 个已改，目录停在新旧混杂的状态。

对照文档 §10.1：先把全部文件移到临时名，再统一写入新名；全部成功才算完成。

**方案（推荐）：两阶段改名 + 可回滚**
1. **预检**
   - 目标名去重用「大小写折叠后的名字」做键。
   - 「目标已存在」只在**它不是本批次的某个源文件**时才算冲突。
   - 校验 Windows 非法字符（`\/:*?"<>|`、控制字符）、保留名（`CON`、`NUL`、`COM1` 等）、结尾的点和空格、长度上限。对照文档 §10.1 的剧名规则可直接沿用。
2. **第一阶段**：所有源文件改名为 `.rename-<批次ID>-<序号>.tmp`。
3. **第二阶段**：临时名改为最终名。
4. **任一步失败**：按相反顺序撤销已完成的步骤。撤销本身也失败时，返回一份「每个文件当前实际叫什么」的清单，并写入日志，不能只报一句「失败」。

**验证**：在 Linux 上用临时目录测互换、链式、只改大小写、中途失败回滚；大小写折叠冲突的用例需要在 Windows CI 上跑，才能证明真的不会覆盖。

### E2 码率修复：判定、校验与轨道问题【中】

**现状与证据**
- 只判断「低于下限」，下限默认 4 Mbps（[crates/dossier-core/src/tools.rs](../crates/dossier-core/src/tools.rs#L94)）。用的是整个文件的码率（`format.bit_rate`，包含音频），不是视频轨。
- 重编码命令没有 `-map`，视频统一 `libx264`、音频统一 `aac`（[toolbox.rs L591-L614](../src-tauri/src/toolbox.rs#L591-L614)）。【推断】多音轨、字幕轨、章节信息会被丢掉。
- 替换原文件前只检查了码率，没检查时长（[L616-L630](../src-tauri/src/toolbox.rs#L616-L630)）。
- 没有停止入口；目前「停止」只能间接靠 B1 的全局变量。

已经做对的：先编到同目录临时文件，达标才 rename 替换，不会跨盘。

**影响**
- 音频码率高的文件，视频轨实际不足 4 Mbps，但会被判定为「达标」。
- 编码异常导致时长变短的文件（例如源文件尾部损坏），只要码率够就会**替换掉原文件**。
- 带多条音轨的原片被悄悄削成单音轨。

**方案**
1. 判定改用视频轨码率；读不到时用「文件码率 − 音频码率」估算，并在报告里标注「估算」。
2. 替换前加时长校验：新旧时长差不超过 `max(0.5 秒, 1%)`，否则删除临时文件、原文件不动。
3. 命令加 `-map 0 -c:a copy -c:s copy`，只重编视频轨，其他轨原样保留。mp4 不支持的字幕格式改为 `-c:s mov_text`，转换不了就跳过字幕轨，并在报告里写明。
4. 接入 B1 的令牌，前端码率修复区加「停止」按钮。

**已确认**（§9 Q7、§9.3）：加上限，默认 8 Mbps、设置里可改；偏低的修到 4.5 Mbps。判定与替换规则以 §9.3 为准。

### E3 挂载文案 CSV【中】

**现状与证据**
- 读取不去 BOM：`read_to_string` 后直接比对表头（[crates/dossier-core/src/publish.rs](../crates/dossier-core/src/publish.rs#L169-L176)）。Excel「另存为 CSV UTF-8」会在开头加 BOM，表头比对必然失败；另存为普通 CSV 是 GBK 编码，`read_to_string` 直接报错。
- 写入不加 BOM（[publish.rs L152](../crates/dossier-core/src/publish.rs#L152)、[src-tauri/src/mount.rs](../src-tauri/src/mount.rs#L143)）。【推断】在 Windows 上双击用 Excel 打开，中文显示为乱码。
- `csv_escape` 只处理逗号、引号和换行（[publish.rs L326-L331](../crates/dossier-core/src/publish.rs#L326-L331)），不防公式注入：AI 生成的文案若以 `=`、`+`、`-`、`@` 开头，Excel 会当作公式执行。
- `generate_mount_copy_csv` 的输出路径完全由前端传入，会自动建目录并覆盖已有文件，不限扩展名（[src-tauri/src/dossier.rs](../src-tauri/src/dossier.rs#L140-L154)）。

**影响**：用户「在 Excel 里改完文案再导回」这条主路径走不通；文案内容可能在 Excel 里触发公式。

**方案**
1. 读取：先去掉 UTF-8 BOM；不是合法 UTF-8 时按 GBK 解码一次（新增依赖 `encoding_rs`，目前 Cargo.lock 中没有）。仍失败则提示「请另存为 CSV UTF-8」。
2. 写入：开头加 UTF-8 BOM（Excel 识别 UTF-8 的标准做法）。
3. 公式注入：单元格以 `= + - @ \t \r` 开头时，在前面加一个英文单引号 `'`（OWASP 推荐做法）。读回时只在「`'` 后面紧跟这些字符」时才去掉，避免误删用户本来就写的单引号。
4. 输出路径：只允许 `.csv` 扩展名；目标已存在时，需要前端显式传 `overwrite: true` 才覆盖。

**已确认**（§9 Q8）：兼容 GBK，引入 `encoding_rs`。

## 7. AI 调用（F）

### F1 生图报错含 "size" 就重试【低】

**现状与证据**：`Err(error) if error.contains("size")`（[src-tauri/src/ai.rs](../src-tauri/src/ai.rs#L234)）。错误文本里只要出现 "size"（比如 `max_size exceeded`、超时信息里带的 `body size`）就会再请求一次，不论是什么错误。

**影响**：可能多扣一次生图费用；真正的错误原因被第二次请求的结果掩盖。

**方案**：只在 HTTP 400、且响应体明确指向 `size` 参数（例如 `"param": "size"`，或错误信息里含 `size` 且同时含 `invalid` / `unsupported`）时才去掉 size 重试。为此 `post` 改为返回结构化结果（状态码 + 响应体），不再用拼接好的字符串做判断。

### F2 AI 返回内容与海报下载没有约束【低】

**现状与证据**
- 剧名、简介只检查非空（[ai.rs L300-L311](../src-tauri/src/ai.rs#L300-L311)），没有长度上限；提示词要求的「8~12 字剧名」不会被强制执行。

### 9.3 E2 码率修复因 Q7 调整后的规则

- 判定：视频轨码率低于下限（默认 4 Mbps）或高于上限（默认 8 Mbps）才处理，其余不动。
- 目标：偏低的修到 4.5 Mbps；偏高的压到 8 Mbps。
- 替换条件：码率落在 [下限, 上限] 内，且时长误差不超过 `max(0.5 秒, 1%)`，才替换原文件。
- 设置：下限、上限都可改，保存时要求「下限 < 上限」。偏低时的修复目标 = `min(下限 + 0.5 Mbps, 上限)`，默认值下就是 4.5 Mbps。

## 15. 第三轮综合审查（安全 + 业务逻辑）

本轮先由三路独立审查对照源码与 USER_GUIDE、MATERIAL_SPEC、README 逐条核实，再写修复方案（经两轮复审、本机 ffmpeg 实测与一次完整性核对）后实施。编号 F1–F20 与方案一致。

### 15.1 问题与处理

| 编号 | 问题 | 后果 | 处理 |
|---|---|---|---|
| F1 | 码率修复的临时文件固定 `.fixing.mp4`，按 mp4 封装后替换原片 | mkv / ts / flv / webm 原片被换成「扩展名不变、内容是 mp4」的文件 | 只处理 mp4 / m4v / mov（显式 `-f mp4` / `-f mov`，临时文件沿用原扩展名）；其余格式不编码、列为失败、原文件不动 |
| F2 | 报审包沿用原文件名；不同子目录的同名分集复制时互相覆盖 | 与 MATERIAL_SPEC 不符；包内少一集，manifest 与分集清单对不上 | 统一命名 `简介.*` / `封面.*` / `第NN集.*`（扩展名跟原文件）；重名按固定顺序加 `-2`；分集清单新增「包内文件名」列 |
| F3 | 深度处理开跑后，材料线程会陆续删过程图、换海报和简介，停止或编码失败时旧 AI 制作证明还留着；去重配方存证编码前就写入 | 目录里留着一张写着旧内容的证明（合规风险）；配方与成片对不上 | 开跑前作废旧证明（删除证明文件，清单里的成片清单清空，海报依据保留）；配方存证改为成片发布后写入；停止 / 失败提示如实说明。关闭材料流水线时旧证明残留的问题一并修复 |
| F4 | 集号解析只认第一个 `第` 和第一个 `e`，独立数字取到分辨率 | `S01E05_1080p` 解析成 1080，拼接顺序错乱 | 扫描全部 `第` / `e` / `ep`，支持 `S01E05`；排除 `1080p`、`4K`、`60fps`、`1920x1080`、`x264` 等；集号相同时按文件名、路径排序 |
| F5 | 单集时长下限设到 3596 以上时 `clamp` 下界大于上界 | 程序崩溃 | 下限钳到 5–3595、上限钳到下限 + 5–3600 |
| F6 | `probe_all` 用 `filter_map(.ok())` 静默丢掉探测失败的分集 | 草稿、挂载文案、转码产物缺集仍报成功；平台对照全部失败时显示「无阻断」 | 返回成功 / 失败两组：产出文件的入口（转码三种模式、导出草稿、挂载文案）拒绝并列出原因；只读分析（转码建议、平台对照、码率检测 / 修复）照常给结果并标明失败项 |
| F7 | 规格缺字段按 0 处理；探测失败显示「尚未探测」 | 误报「时长低于下限」；与报审包的拒绝说法不一 | 读不到时长 / 分辨率 / 码率时警告人工确认；探测失败判为不通过；简介读不出单独提示 |
| F8 | 重复集号、缺集不检查 | 用户不知道报审包会出现 `-2` 后缀 | 新增「集号」警告项（不拦截） |
| F9 | 报审包分集清单 CSV 无公式注入防护、无 BOM | Excel 打开可能执行公式、中文乱码 | 复用挂载文案的转义；所有文本列转义；带 BOM |
| F10 | 成本表数值不限小数、`\|` 破坏表格；后端不校验数值 | `0.30000000000000004 万元`；表格错位 | 最多两位小数；`\|` 转义为 `\\|`、换行换空格；后端拒绝非有限值、负数与超过 100 的占比 |
| F11 | AI 制作证明只写了 3 个被改写的元数据字段，实际改了 5 个 | 证明与成片不符 | 字段表由 `dedup::METADATA_FIELDS` 统一提供，写元数据与证明共用 |
| F12 | AI 剧名超 15 字时剧名、简介整组作废 | 合格的简介也丢掉，下次重试再付费 | 两项分别判定，只作废超长的那一项并说明原因 |
| F13 | 生成流水按行读，遇到非 UTF-8 行停止 | 之后的记录全部不显示 | 整份读入后宽松解码，坏行只跳过自己 |
| F14 | 码率偏低时第二遍目标可能超过上限 | 窄区间（如 4–5 Mbps）下第二遍必然超标 | 上界取 `min(下限 × 2, 上限)` |
| F15 | 跨源重组某段编码失败时，正在写的那一段不清理 | 输出目录留下半截隐藏片段 | 失败分支一并删除 |
| F16 | 按目标集数重组切出的段数不足时不提示 | 用户以为拿到了要的集数 | 完成说明写明「素材只能切成 N 集（目标 M 集）」 |
| F17 | 去重验证的剧名 / 角标 / 水印 / 路径分两个参数传 | 以 `-` 开头的值被 argparse 当成选项 | 全部改为 `--key=value` 一个参数（已用真实 argparse 复现与验证） |
| F18 | 写进用户目录的原子写入用可预测的临时名 + `fs::write`；挂载文案直接写文件；`exists()` 跟随链接 | 预先放好的符号链接可让写入落到别处 | 新增 `fsio::write_atomic`（`create_new` 独占创建临时文件，被占时换名）；挂载文案、清单、海报、配方、归属标记、重组清单都走它；存在判断改用 `symlink_metadata` |
| F19 | 编码前不清理同名旧临时文件 | ffmpeg 顺着残留链接写到别处 | 新增 `fsio::clear_stale_temp`，在 `.part`、`.fixing`、重组片段、角标写入前调用；遇到真实目录报错不删 |
| F20 | 智能微调沿用原扩展名，webm 编不出来；不同子目录同名分集并行写同一个文件 | 难懂的 ffmpeg 报错；输出内容不确定 | 开始前检查，有 webm 或同名分集就整批拒绝并列出文件 |

### 15.2 用户看得到的行为变化

- 报审包里的文件改为统一命名；与旧版报审包做差异对比时，改名的文件显示为一批新增与移除。
- 智能微调遇到探测失败的分集、webm 素材或同名分集时整批拒绝（以前跳过坏集照常处理）。
- 集号修正后，以前按错误集号保存的挂载文案 CSV 重新校验时会提示集号对不上，重新生成即可；重组 / 深度处理的拼接顺序也随之改正。
- 在已有输出目录上做深度处理，中途停止或失败后上一轮的 AI 制作证明会作废，需要完整重跑一次才会生成新证明。
- 去重配方存证只在成片全部完成后写入。
- 码率修复不再处理 mkv、ts、flv、webm，这些分集列为失败并说明原因。

### 15.3 本轮不修

| 项 | 理由 |
|---|---|
| 批量改名 / 挂载 CSV / `open_path` 可作用于任意目录 | 需要前端先被注入脚本；目前没有注入点，CSP 禁止内联脚本。记入加固待办 |
| 打包时复制素材会跟随链接 | 需要用户自己的素材目录里有指向私密文件的链接 |
| 本地演示账号哈希弱、Windows 盐值可预测 | 只在本机文件里；账号功能转正式时必须重做 |
| 激活新卡时时钟下限重置 | 设计取舍，激活需要服务器签发 |
| 深度处理重组阶段超时系数为 4 | 等低配机实测后统一调整 |
| 擦除不能中途停止 | 文档未承诺 |
| 手填剧名不限 15 字 | 文档只约束 AI 生成的剧名 |
| 平台对照缺封面时按集数重复计数 | 只影响计数显示 |
| 手改 settings.json 后规则不立即校验 | 探测完成后会校验并报错 |
| 设置、挂载计划、checkpoint、pipeline 印记的临时文件名可预测 | 设置与挂载计划在应用配置目录；后两者只有命令行工具使用，桌面应用不调用 |
| mkv 原片带图形字幕时智能微调可能失败 | ffmpeg 会明确报错，不损坏文件；已写入 USER_GUIDE |

### 15.4 实施后复审（两路：对照方案逐条核对、只看改动找回归）

| 问题 | 后果 | 处理 |
|---|---|---|
| 缺号检查把集号最小到最大的整段区间收集进内存；E 标记不做 1–9999 范围过滤 | `E4294967295.mp4` 这类异常文件名可让检查分配约 16GB 内存 | 只计数、样本最多 20 个；E 标记与独立数字共用范围过滤 |
| 作废证明先删文件后写清单；清单只清了成片清单，过程图计数还在 | 写清单失败时提示「未开始处理」与实际不符；作废后重做海报会写「已生成 4 张过程图」，而过程图已被删 | 先写清单再删文件；过程图计数清零、来源写「未生成」；只清掉成片清单时也算作废 |
| 材料流水线关着时，深度处理作废了旧证明却不生成新证明，完成说明不提 | 用户以为目录里还有证明 | 成功但未生成新证明时，完成说明末尾如实提示 |
| 配方存证在成功后写入失败时，报告读到的是上一轮留下的存证 | 报告把旧配方当成本轮 | 写入失败时删掉上一轮存证，报告不再引用 |
| 码率检测有探测失败的行时，标题仍是绿色「0 集超出」；失败行堆在表尾 | 容易忽略失败项 | 有失败行时标题标红并写明失败集数；失败行按原分集顺序插回 |
| 集号解析：`_v2`、`1080p60`、`H.264` 仍会被当成集号 | `剧名_05_v2` 解析成 2 | 排除词首的 `v` + 数字、`p` 后紧跟的帧率、`h.264` / `h.265` |
| ts / flv 没有文件码率时每集多一条「读不到码率」 | 正常素材也出现一排警告 | 文件码率与视频轨码率都读不到才提示 |
| 码率修复按文件名查时长（旧问题） | 不同子目录同名分集拿到同一个时长，时长校验出错 | 改按完整路径查 |
| USER_GUIDE 对编码失败与停止的描述混在一起；附录 A 重名排序少写「有集号在前」 | 文档与代码不符 | 分开写停止 / 编码失败 / 成功未出证明三种情况；补全排序规则 |

本轮仍不改：写文件改为「新建再改名替换」后，原文件的权限、ACL 与硬链接不保留（输出目录里的文件均由本程序生成，可以接受）；同名判断在 Linux 上也不区分大小写（偏保守，避免拷到 Windows / macOS 时冲突）。

### 15.5 第 2 轮实施复审

| 问题 | 后果 | 处理 |
|---|---|---|
| 作废证明时无条件把过程图计数清零，但材料流水线关着时旧过程图不会被删 | 清单记 0 张而磁盘上还有 4 张，重做海报出的证明与目录不符 | 流水线开着时一并删除旧过程图并清零；关着时过程图与计数都原样保留 |
| 缺号计数 `max - min + 1` 用 u32 计算；`第` 标记不做范围过滤 | `第0集` 与 `第4294967295集` 同时出现时调试构建 panic | 改用 u64 计算；`第` 标记也只认 1–9999 |
| 版本号规则把 `v05_1080p` 里唯一的集号也排除了 | 解析成 1080（上一版是 5） | 只有前面已有干净集号时才把词首 `v` 后的数字当版本号 |
| 配方存证写入失败时完成说明仍写「存证于 去重配方.json」；本轮关去重时上一轮存证留在目录 | 说明与实际不符；旧配方与本轮成片放在一起 | 写入失败时说明改为「配方存证写入失败」；关去重时删除上一轮存证 |

仍不改：清单损坏且证明文件本来就不存在时不追加「已作废」提示（没有可作废的东西，属实）；`write_atomic` 不保留原文件权限与硬链接、同名判断在 Linux 上也不区分大小写（同 15.4）。

### 15.6 AI 制作证明生成流程专项检查

| 问题 | 后果 | 处理 |
|---|---|---|
| 三个排版脚本（证明、角标、过程图）找不到中文字体时退回 Pillow 内置默认字体，它没有汉字 | 每个汉字画成同一个方块，脚本照样「成功」：证明看不清，角标烧进每一帧也看不清，界面不提示（本机实测「中」「剧」「证」三字像素完全相同） | 新增共用模块 `tools/process_images/cjk_font.py`：补全 macOS / Windows 候选字体，并实际画三个汉字检验字形互不相同；找不到能画汉字的字体就报错退出。证明随之改出文本版并写明原因，角标让深度处理在编码前停下，过程图记警告且一张都不写出 |
| 证明日期在材料线程开始时取，收尾时不更新 | 深度处理跨过午夜时，证明日期早一天 | 收尾生成证明与重做海报时都刷新为当前北京时间 |
| 收尾计算成片指纹时检查停止令牌 | 编码刚完成就点停止，成片已发布，证明却写「成片清单未记录」 | 收尾算指纹不接停止令牌（只读文件）；`finalize_deep_proof` 去掉停止参数 |
| 证明数据临时文件与三个脚本的 PNG 直接写入 | 可能顺着输出目录里预置的符号链接写到别处（与 F19 同类、当时漏掉） | 证明数据改走 `write_atomic`；脚本 PNG 改为 `mkstemp` 独占临时文件 + `os.replace` |
| 排版脚本没有自动测试 | 上面的方块问题一直没被发现 | 新增 `tools/process_images/tests`（12 例：缺字体必须报错且不写文件、正常出图、不跟随符号链接、以 `-` 开头的剧名与角标文案），接入 `scripts/check.sh --py` 与 CI；反向验证：退回默认字体时 4 例失败 |

顺带：证明与过程图脚本的参数改为 `--key=value`（以 `-` 开头的剧名不再被当成选项）；角标失败提示按原因区分「安装中文字体」与「联网安装 Pillow」。
